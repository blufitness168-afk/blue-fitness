# R2 — staff password reset (prepare-only)

18 Nov 2026. Bounded slice, not R2 completion or production acceptance. Security follow-up explicitly changes only existing login issuance and password-completion finalization lock protocols; other auth/profile flows, role permissions and old migrations remain unchanged. TODO unchanged.

## Scope / contract

- ADMIN → MEMBER only; OWNER → MEMBER/ADMIN only. No OWNER target, no self, no suspended actor/target. Expired/PENDING members are allowed, matching password auth's suspension-only restriction; no membership status/expiry mutation.
- POST `/api/admin/members/[memberCode]/password`: strict `{requestKey: UUID, reason: string (trimmed 1–240), password: string (10–128)}`. Uses existing `auth/registration.ts` password policy without trimming/normalizing the password and existing `auth/password.ts` salted scrypt / runtime work cap (2 jobs, no queue).
- Target comes only from route. No actor/role/status/hash/token/target fields accepted from body. Same-origin, persisted NORMAL/live session, bounded 4 KiB JSON, generic errors, allowlisted `{ok:true}` only. Unknown SQL/transport results never become success.
- Separate form on member detail under existing conservative role gating plus self/suspended exclusion. No changes to profile editor, history, monetary projections or role controls.
- Password + frozen serialized body exist in transient form/request memory only. No browser storage, URLs, logs, response echo or password prop from server. Inputs clear after submission; the in-memory body remains available for manual exact retries until success, reload/unmount or explicit discard. JS/React/network buffers cannot be securely zeroed; no claim of secure memory erasure. Browser password-manager behavior is outside application control (`new-password` autocomplete).
- Staff must not enter passwords, OTPs, session values or other secrets in reason. API rejects a reason containing the submitted password verbatim; it cannot identify arbitrary unrelated secrets supplied as free text.

## Two-phase SQL protocol

`20261118_R2_admin_member_password.sql` adds request/audit tables and `admin_member_password_action(text,uuid,jsonb,text DEFAULT NULL)`. SECURITY INVOKER, fixed search_path, PUBLIC privileges revoked, same trusted server DB-principal model as existing profile SQL. No new application role/grant/dependency. The server-only rollout gate is documented below.

Both phases first discover the actor session without locking it, then lock actor/target member rows in stable ID order, then reread and share-lock the actor session. The locked session must still belong to the discovered actor and be NORMAL/unrevoked/unexpired. Independently reread live actor status/role and target status/role under member locks; recheck expiry before claim/success. Initial unlocked discovery is never authorization. All reset member locks precede actor-session and target-session revocation locks, removing the OWNER-reset-ADMIN versus ADMIN-reset-MEMBER session/member inversion.

1. **Claim transaction (no password/hash supplied):** validates exactly `{memberCode,reason,bodyMac}`, serializes actor/key through actor row lock and quotas through a fixed global advisory transaction lock. Persist one actor/key claim. Admit at most 5 claims/actor/15 minutes, 3/target/15 minutes, 50 globally/minute. Abandoned claims count. Existing pending key returns busy; mismatched binding conflicts; completed exact binding returns historical success. No automatic claim retries, lease stealing or second scrypt for a pending key.
2. **Hash outside transaction:** only explicit `claimed` starts existing scrypt. Work-limit rejection/crash leaves claim pending, not reissued. No durable raw password, additional credential hash or hash work queue.
3. **Finalize transaction:** reauthorizes, locks the request, requires uncompleted claim younger than 2 minutes and unchanged target MVCC `xmin`. This is an intentionally conservative short-lived stale-write guard: *any* intervening target UPDATE (even unrelated profile/points updates) rejects. It is not a reusable application revision, timestamp, credential digest or audit field. Claim and finalize are separate autocommit statements/transactions; do not wrap both in one transaction. Table rewrites/freeze/maintenance and XID wraparound are not supported coordination mechanisms; require quiescence for maintenance, and retain the short deadline. No reliance on client timestamps.
4. Update **only `members.password_hash` and `updated_at`**, revoke all unrevoked target sessions (all modes), consume target PASSWORD_SETUP/PASSWORD_RESET challenges and all target password tickets, insert metadata audit and mark completion in the same transaction. Audit/finalization failure rolls everything back, but the separately committed claim remains reserved. Unrelated accounts, REGISTER/signup tickets and finance are not modified.

### Scoped auth coordination follow-up

- `loginPassword` still reserves its existing rate limit and verifies scrypt outside the issuance transaction. Issuance now runs **two ordered statements in one Serializable transaction**: `SELECT ... FROM members WHERE id=... FOR UPDATE`, then `INSERT ... SELECT` rechecking the exact verified credential hash and current non-suspended status. The member lock is held through commit, not inferred from the session FK. If login commits first, a later reset waits and revokes that session. If reset wins first, issuance observes a mismatch or fails with serialization conflict. The function does not return token/success until the transaction promise (including commit) resolves. Lock/statement/commit errors propagate without blind retry.
- `completePassword` preserves the existing one-shot pre-scrypt ticket claim. Finalization now first does an **unlocked ticket lookup to identify and lock its member `FOR UPDATE`**, in a separate first statement of the same Serializable transaction; only then does the existing consume/change/revoke CTE run. Ticket consumption additionally rechecks the member's current hash/status/setup-reset applicability, and member mutation retains its original issuance-hash guard. This removes finalization's ticket→member inversion against reset's member→ticket order. The pre-hash claim only updates the ticket and reads member state without a member row lock; it commits before scrypt/finalization and is never held while waiting for a member lock.
- Reset and completion hold their member locks while revoking sessions/challenges/tickets. Neither an old-password login nor an in-flight claimed ticket may overwrite a newer completed reset through the scoped paths. Unrelated registration, OTP issuance/verification, kiosk and profile protocols are unchanged.
- **Remaining gate:** no multi-connection PostgreSQL race/deadlock proof was run. Existing profile SQL still locks session→member and is outside this follow-up's authorized scope; mixing it with member→session resets can still deadlock. PostgreSQL aborts a participant (availability/unknown-result issue, not authorization bypass); reset remains atomic and fails closed, and the application does not blindly retry. Do not claim global deadlock freedom or production acceptance. A separate review/UAT is required before rollout.
- Deploy coordinated auth changes before enabling staff reset and drain old app instances/in-flight old-protocol work. Rolling back only login/finalization while leaving staff reset enabled reintroduces the security race and is not supported.

## Idempotency / secret handling

- Server computes HMAC-SHA256 with existing **`SMS_API_SECRET`**, over domain-separated JSON array `["blu:admin-member-password:v1", actorId, memberCode, requestKey, normalizedReason, exactPassword]`. No new secret. Missing secret fails closed before SQL/hash.
- HMAC is stored **only in the restricted request table**, never audit/response/log/client. It is not an unkeyed password hash, salt/hash copy or offline-verifiable password fingerprint without the server secret. An attacker obtaining both DB request records and this secret could perform dictionary guesses; protect this existing high-entropy server secret independently of DB backups. This implementation does not inspect or print its real value. Existing secret must be strong; no fallback to a public value/DB URL/session cookie.
- Audit is append-only: ID, actor ID/current role, target ID, UUID, reason, timestamp **only**. No password/hash, HMAC/body digest, token/session digest, target version, before/after member serialization or phone. Audit trigger blocks UPDATE/DELETE/TRUNCATE; DB owners can bypass protection, so this is not tamper-proof against malicious DB administrators.
- Same actor/key + target/reason/password returns historical success after completion, **without** updating credentials, revoking new sessions or consuming newly issued tickets, even after a newer legitimate password change. Different target/reason/password with that key conflicts *before* scrypt, both pending and completed. All replays still reauthorize current session/roles/status.
- Retry must retain identical UUID and body. A busy/failed hash cannot resume that key: wait for the 2-minute completion deadline, then consciously start a new UUID (subject to quotas). Never automatically make a new UUID after an unknown response; old work may have completed. Reload discards the only browser copy, not the server claim. The UI explicitly warns about historical success and reload/discard semantics.
- Secret rotation changes the HMAC, so old UUID replays fail closed as conflicts; it cannot reopen a completed request or reset credentials again. No old-secret fallback. Retention/cleanup is intentionally not implemented: deleting request keys would remove historical replay protection. Audit is never used as a password verifier.

## Prepare-only rollout / rollback

Production profile/contact changes are applied; the password migration is **not applied**, pending coordinated auth deployment/drain. This task does not apply any migration.

Staff reset UI/API default **OFF**. Only the exact server environment value `ENABLE_ADMIN_PASSWORD_RESET=true` enables them; unset, empty, `false`, or any other value stays disabled. Never use a `NEXT_PUBLIC_` variant. The shared `server-only` helper gates the server-rendered page (no reset form while off) and API. The API preserves the same-origin guard, then returns a generic `503` while disabled, before auth lookup, body parsing, HMAC/digest, SQL client/query or scrypt. Enabled requests retain all existing authorization guards. No environment files are changed by this work.

Keep the gate unset/false across all instances while deploying coordinated login/password-completion protocols, draining old instances and in-flight old-protocol work, applying the separately authorized password migration, and completing the race/deadlock review/UAT gates. Only enable after these prerequisites pass. To disable, unset/set false and restart/redeploy all instances; this blocks new requests but does not cancel already-running resets, so drain them before any auth-protocol rollback. Preserve request/audit history.

Password migration requires existing members, hardened password OTP/ticket schema (`20261009_password_welcome.sql`, `20261009_auth_review_hardening.sql`) and NORMAL/KIOSK session migration. No dependency on R3–R7 or the profile migration.

Before separately authorized rollout: backup; inventory deployed schema/migrations; rehearse on disposable PostgreSQL; review same trusted server principal ownership/permissions on members/auth tables/new objects; verify secret management and logging/redaction at DB/proxy/APM level. Application emits no SQL/error/request logging, but cannot configure external infrastructure logging within this slice. Do not grant browser/PUBLIC access. Migration owner/server principal must retain required invoker privileges; migration does not invent/broaden DB roles.

Rollback application/API first; preserve both request and audit tables. Do not drop/rewrite credentials, undo resets from snapshots, resurrect sessions/tickets or delete historical request keys. No plaintext credential or durable credential copy exists for undo.
