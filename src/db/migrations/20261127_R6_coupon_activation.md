# R6 — General coupon activation (prepare only)

Requires `20261024_real_benefits_admin.sql`. No R3/R4/R5, time-supplement or payment migration changes. This is additive SQL plus an in-place replacement of the existing benefits action (retains its ACL). Do not use `db:push` to deploy, and do not run this migration automatically.

- The admin form opts in new `FRIEND_PASS` and `EXTRA_DAYS` definitions via `create_r6_coupon`; explicit JSON `null` means no post-activation time limit, `0` means 10 minutes, and a positive integer is minutes. The old SQL rejects the new action. Old clients that omit the field retain the existing create/replay contract; previously created definitions and any grants from them stay legacy. Promo, welcome, package and time-supplement coupons are not opted in.
- Each new grant snapshots its campaign deadline and duration. The owner of the coupon uses a normal session to activate it explicitly. The database clock is read after row locks; activation never consumes quota or changes membership. The coupon ID identifies the original receipt even if a retry arrives after use, expiry or cancellation. The wallet, not the historical receipt, gives current status.
- `expire_date` is the campaign deadline until activation and the earlier of the campaign deadline and duration deadline thereafter. Consumption at or after that instant is rejected under lock. Cancellation invalidates the coupon without changing the R6 activation receipt. Definition deactivation retains the existing behavior: blocks new grants, does not invalidate issued coupons.
- Apply only after rehearsal and explicit deployment approval. Check that the trusted application role can read the new columns and execute `public.r6_activate_coupon(text,integer)` with the necessary invoker table privileges; no default `PUBLIC` execute grant. Verify app/database compatibility and both ADMIN/OWNER and member sessions before enabling new creation. Do not restore the pre-R6 consume routine while R6 grants exist; it lacks the pending-activation guard. Prefer a forward fix; keep issued grants and their receipts.

Native regression: `python -B scripts/r6-coupon-activation-postgres-test.py --bin-dir <native PostgreSQL bin> [--psql <client>]`. The runner starts its own loopback SCRAM cluster and does not read app credentials. Uses a minimal base fixture plus actual benefits/payment prerequisites; not a full production-schema rehearsal.

Out of scope: additional coupon kinds, recipient targeting, campaign-wide/per-member quota redesign, promo/payment changes, and the full R6 checkpoint.
