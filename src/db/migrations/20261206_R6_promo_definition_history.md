# R6 promo definitions and history — prepare only

Append `20261206_R6_promo_definition_history.sql` after `20261205_R36_current_term_targeting.sql` and its prerequisites. Deploy schema before exposing new definition fields. It adds a read-only projection and patches only `r6_create_scoped_promo(text,uuid,jsonb)` (same signature and ACL). No updates to R36/R347, checkout coupon policy, payment/reservation rules, existing grants or audit receipts.

- `promoDescription`: optional text, maximum 500 chars. `promoRecipientLimit`: optional integer 1–1,000,000. Blank means unlimited. It counts lifetime assignments (including cancelled), independently of the existing total use/reservation limit. The existing writer permits one assignment per member per code; the cap is enforced at grant confirmation, not guaranteed by preview. No updates to already issued definitions.
- Staff/member promo history is assignment-based, 50 per page, with filters for promo name, exact promo code, status and package duration **at grant** (plus member code for staff). Old rows with no recorded duration remain visible unfiltered. The history uses reservation rows linked to the assignment and never infers a usage timestamp from an unlinked order. `ASSIGNED` is not a guarantee of available purchase quota or match to a specific cart. No actual order amounts, order IDs, provider data or audit payloads leave the history endpoint. The legacy OWNER payment-detail section is unchanged.
- Existing promo checkout is unchanged. In particular, `PENDING` holds through upload deadline or while a persisted `PROCESSING`/`UNKNOWN`/`VERIFIED` attempt exists; this slice does not tighten old reservation/release rules or change how cancellation/refund works. No batch/auto-grant and no new scanner or eligibility resolution. Eligible packages in wallet history show catalog IDs; definition management already shows current catalog names when available.
- Grant `EXECUTE` on `public.r6_promo_history(text,boolean,integer,text,text,text,integer)` to the trusted invoker runtime only (not `PUBLIC`). Validate runtime SELECT access to `auth_sessions`, `members`, `benefit_definitions`, `benefit_assignments`, `benefit_promo_reservations`, `package_payment_orders` and `package_payment_attempts`. Verify the existing grant role can lock definitions and read assignments. No browser/real provider or production-role verification was performed.
