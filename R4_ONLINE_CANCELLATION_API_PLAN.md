# R4 — Online cancellation: evidence prepared, writer not implemented

## What this change does

`src/db/migrations/20261124_R4_online_settlement_evidence.sql` is a new, **unapplied** migration. It adds no API, refund ledger, cancellation marker, or entitlement/reversal writer. It does not change customer cancellation before slip submission, existing reader behavior, or historical rows. Old PAID (even with an R4 observation) remains unsupported. PENDING orders created before installation are covered only if they settle after installation through the verified path.

The migration checks the reviewed finalizer body (October PromptPay + NORMAL session patch + receiver-bank fix), invoker/search path/owner/ACL, and the terminal, benefit-issuance, and R4 observation trigger bodies/wiring. It patches two positions in the same finalizer, retaining its signature, ACL and control flow. After successful evidence/transfer checks, and immediately before member mutation, it records the actual locked prior expiry (including NULL), status, points, member, order, and verified attempt. An AFTER trigger following issuance and observation matches the pre-state to the same `xid8` and verifies the resulting member state, PAID order, original transfer claim, observation, award, and exact issued friend/extra-days coupon identities and issuance values. It also records the existing promo assignment link when present; it does not release or restore it. The finalizer asserts the post-state row exists before returning. Terminal replay does not recapture. The two evidence tables are private and append-only; no evidence payload, session token or bank identity is copied. Missing/mismatched evidence or capture failure rolls back settlement, not just the evidence row. No live data or transaction history is used to infer prior state.

Settlement also captures a SHA-256 fingerprint of that member's check-in rows, ordered by ID and rendered in UTC. Native tests verify that it changes even when a scan waits for settlement, uses the new PAID entitlement, and records a timestamp earlier than `confirmed_at`. A mismatch is a review blocker; equality alone is not authorization, since all check-in writers must serialize with any future reversal. This is aggregate provenance, **not** proof of a prior entitlement's identity, coupon non-use, point-lot non-use or absence of subsequent effects. It must not alone authorize reversal. The DB owner remains trusted; this is not an audit boundary against privileged DDL or forged writes by that owner.

## Before applying the evidence migration (separate approval)

Rehearse against the exact installed function/trigger definitions, migration order, real backend role, grants/default grants, schema ownership/CREATE privileges and transaction execution path on a disposable clone. This migration deliberately supports a trusted owner/invoker path: apply as the finalizer's owner; no named direct EXECUTE grants to other roles, no PUBLIC execution, and no additional grants on the private objects. Confirm the settlement connection executes with the effective owner privileges, including on the new private objects. A split-role or changed-definition install is **not** supported blindly; review the privilege design and run successful and failing settlement as the actual backend role before rollout. Do not grant evidence writes to client roles as a workaround.

Confirm backups/restore and a controlled writer pause for the short exclusive order-table lock. The migration is atomic with a lock timeout. Monitor verified pending retries and evidence coverage after rollout. If a rollback is needed, pause writers and restore the exact reviewed finalizer definition and remove the new order hook atomically; retain both immutable evidence tables and record the coverage gap. Do not drop evidence, backfill, or retry against a provider merely because finalization rolled back.

## Proposed API and acceptance gates (not implemented)

- **Preview:** an OWNER-only, uncached `GET /api/owner/online-cancellations/:orderId` returns a narrow order summary, amount in satang, and `eligible` or a typed blocker. It must be clear that preview neither refunds nor guarantees the subsequent write. Do not expose evidence, financial payloads or eligibility reasons to ADMIN or members.
- **Record:** `POST` to the same route accepts a UUID idempotency key, confirmed external full refund amount, bounded reason/reference and explicit confirmation. Require current NORMAL OWNER session at the route and under the SQL locks; enforce same-origin/CSRF protections. No provider request. SQL binds the key to actor + canonical payload, returns the existing receipt for exact replay, rejects key collisions and enforces one cancellation per original order across keys. Use `409` for state conflicts/ineligible orders, a distinct retryable response for ambiguous transport failures, and keep retry keys stable. Re-evaluate eligibility under lock; never use preview as authority or update a PAID row.
- **Write gate:** first support only cases proven safe. Require both evidence rows, expected member aggregate, proven tenure and exact dependent grants, no successor or conflicting pending/staff term, no check-in/visit or benefit use attributable or possibly attributable to this sale, and no spend that could have drawn its award. A sufficient balance does not prove award non-use. Unprovable chronology, promo dependencies, manual adjustments, R3 override/R6 changes, or ambiguous concurrent writes require manual review, not an override. Use shared lock order with settlement, purchase, admission, reward and benefit writers and prove all branches serialize. Atomically append cancellation, point compensation, coupon revocation as proven, and a finance offset for exactly the original paid amount; preserve all source rows. Do not mutate any aggregate until the cancellation-aware projection and exact reversal are proven.
- **Reader gate:** keep `paymentAccount`/`RealPaymentAccount` purchase history separate from current entitlement. Align kiosk, front desk and supported R6/R7 admissions with the same current-term predicate. Include compensation/revocation in `real-member-wallet-server.ts` and every eligibility/use path. Include one refund entry in OWNER `real_finance_action` on both October and R5 variants and in Excel/export, while retaining the original income. Audit staff renewal eligibility, online repurchase, R3 override and latest-PAID direct reads, too. Install/read-test these paths before granting any writer or enabling a route/flag. Unsupported stacks must reject enablement rather than fall back to legacy reads.
- **Release test:** prove cross-view agreement including historical PAID, cancelled coupon/points, finance/refund and export; test legacy/no-evidence, partial refunds, ROLE/session failure, used rights, uncertain pooled-point spend, chained terms, duplicate keys, concurrency with admission/spend/purchase/settlement, rollback and regressions including pre-slip customer cancellation. Require browser and actual deployment-role rehearsal before enabling.

## Restricted writer: remaining release blockers

- The native blocker test now settles a coupon-free order with NULL prior expiry and unchanged aggregate/fingerprint. Restoring the exact recorded aggregate in a rolled-back fixture still leaves that sale selected as `paymentAccount.package`. After a real repurchase settles, `r3_override_current_order` returns no row because it counts the retained original PAID; an otherwise equivalent one-sale control passes. Do not remove retained PAID rows or relax R3's ambiguity check globally. Make current-term lookups (including the R3/R6 competing-order checks and R7's separate PAID lookup for visit snapshots) exclude only proven cancelled orders; keep purchase history intact. Wallet compensation and both finance/Excel projections still need verified readers.
- `checkin_fingerprint` is a content comparison, not a lock. The native evidence test proves the front-desk path can write a visit with a timestamp earlier than confirmation, so a timestamp-only exclusion is unsafe. `real_rewards_action` locks the member before spend, but `redeemWelcomeEntry` updates the coupon then inserts a check-in directly without an explicit member row lock. Do not assume a member lock alone fences every fingerprint writer: verify actual FK/trigger locking or move that path under the shared member-first lock, then test the locked recheck against admission, welcome redemption, spend, purchase, and settlement. No refund API or writer is implemented.

The test creates a fresh SCRAM loopback PostgreSQL cluster with synthetic fixtures only (no app environment or existing database). It covers October finance + staff flows, R5 finance + staff flows, and R5/R6/R7 as a separate stack, not an unsupported combined staff + R6/R7 deployment. It exercises the installed finalizer, NULL/past/future prior expiry, point and coupon effects, pending-at-installation coverage, unchanged old PAID, ACL and append-only guards, baseline drift, transaction rollback, injected capture failure, terminal rejection/replay, and concurrent settlement waiting on the member lock. This tests settlement evidence, not cancellation, production ACL, provider calls, or browser acceptance.
